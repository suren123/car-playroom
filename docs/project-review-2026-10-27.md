**影响品质的具体原因**

1. 操作结果主要体现为文字、数字和按钮状态。红绿灯正确时推进索引；排队车辆并没有真实驶离队伍；改道是选择按钮后直接完成。孩子对汽车有兴趣，持续吸引他的应当包括“车真的停下、转弯、装货、卸货、过桥、回库”。这些动作应清楚解释规则的结果。
2. 内容变化比较薄。修车是固定三题，修桥是三个地点重复四块桥板；找不同主要替换整辆车的车型。更换随机排列能增加题目数量，但不会自动增加新的观察方法、决策或互动。
3. 教学还主要靠句子。4 岁孩子需要看一次具体示范，再立即做一个简单动作。现有第三层“示范”主要是手指图标和目标闪动，尚未演示“把什么送到哪里”。
4. 记忆负荷没有被单独设计。听指挥的目的地顺序和当前步骤一直显示，适合作为教学支架；如果目标是练习记住信息，就需要另设“看/听 → 收起提示 → 记住并执行”的阶段。
5. 难度变化有跨度。数独完成一次 2×2 教学后，下一局默认进入 4×4；修车/修桥的 `level` 目前只进入记录，没有改变题目。自动升降主要根据选错和提示次数，不能据此判断孩子是否独立理解。
6. 视觉缺少统一生产规范。菜单 emoji、两套汽车 SVG、图标与人物造型同时存在；同一辆车尚没有跨游戏一致的素材 ID、动作状态和可替换部件。

证据位置：`components/playroom.tsx`、`components/road-games.tsx`、`components/legacy-game.tsx`、`components/vehicle-art.tsx`、`components/car-art.tsx`、`lib/game.ts`、`lib/replay-games.ts`、`lib/road-games.ts`。

**产品组织建议**

儿童入口采用具体地点和行为，例如“去送货”“去救援”“去停车”“看看车库”，配统一插画。家长可以按“记住再做、仔细观察、轮流合作、换个办法”等标签选择，标签背后的认知目标放在家长说明里。

阶段目标可设为 2 款精品游戏和 6–8 个小游戏。首页优先展示 4–6 个熟悉入口，加上“接着玩”“最近喜欢”；完整目录可以再展开。无需为了数量把每一个小游戏都做成独立的大型世界。

精品游戏具有完整的进入、演示、操作、场景变化、结束过程，有少量手工设计的关卡与可控变化。小游戏每局只承载一个清楚的规则，适合短时间重玩；“小游戏”同样应使用完整声音、触控和退出规范。

**两款精品的具体方向**

“汽车快递站”：家长和孩子给汽车小镇送装备。初期清单一直显示，认识装货和送货；熟悉后，先看 1–2 件货物，再由孩子点“记好了”，清单收起，选货装车。随后进入两个地点的送货顺序，最后才加入“送掉一件后，记住还需要哪件”的更新任务。每次装货、出发、到站、卸货都有对应画面和声音，完成一段小行程后主动结束。

它可承载视觉短时记忆、顺序记忆和工作记忆的不同玩法，但应在关卡配置和家长说明中区分。单纯记住两张图并复现主要是短时保持；保持清单、按规则执行并更新剩余目标，才进一步增加了工作记忆需求。初期不要在同一关同时增加物品数量、相似度、等待时间和操作步骤。

“汽车小镇救援队”：保留消防车的兴趣入口，把红绿灯、轮流过桥、选择道路做成场景。每关围绕一个主要约定展开：到停止线前停车；一辆车过桥，另一辆在等待区；遇到施工后共同选择另一条可行路线。家长有真实角色，例如决定另一辆车何时准备好、轮流放置桥板、邀请孩子给出指令。道路变化提前示意，孩子始终可以求助、重试或暂停。

两款游戏各先完成 6–8 个经过挑选的基础关卡，再加入相同规则下的可控题目变化。不要把所有已有小游戏拼成一条必须做完的长任务链。

**适合补充的记忆与观察小游戏**

| 游戏 | 核心过程 | 主要练习机会 | 初期设置与变化方向 |
| --- | --- | --- | --- |
| 车库里少了谁 | 看几辆车 → 孩子确认看好了 → 车库门关闭后少一辆 → 选出缺少的车 | 视觉短时记忆、变化辨别 | 从 2 辆差别明显的车开始，再增加到 3 辆；不先加相似车干扰 |
| 小车停在哪里 | 看车停的位置 → 收起车辆 → 把车送回对应位置 | 视觉空间记忆 | 两个车位、两辆车，之后只增加位置数量或车辆数量之一 |
| 汽车翻翻配对 | 翻两块车库门，找相同车辆 | 位置记忆、匹配与轮流 | 先 2 对；可亲子合作，保留已匹配车辆；不设置对抗输赢 |
| 听完再出发 | 听一站/两站指令 → 收起路线卡 → 依次开到目的地 | 听觉顺序记忆、按顺序执行 | 从一站学操作，再尝试两站；允许主动重听，不把重听当失败 |
| 记清单来装车 | 记住物品 → 收起清单 → 在货架选取 → 交货后更新剩余物品 | 记忆保持与更新 | 两件物品、低干扰；之后再引入一件已送达、剩余一件的更新 |
| 停车规则换一换 | 先按颜色停 → 清楚展示新规则 → 改按车型停 | 规则理解、认知灵活性 | 切换前演示；不在孩子不知情时偷偷改规则 |

找不同应继续作为观察玩法，与“先看后隐藏”的记忆版本分别呈现。数独和找不同不应都被笼统标成“工作记忆训练”。每关一个主要目标，允许多个过程共同参与。

这些数量仅是起点建议。观察阶段可以由孩子点“看好了”结束；即使后续使用短暂展示，也应允许延长、重复和家长支持，不引入抢时间、扣分或必须赶在倒计时前完成的压力。

**素材应该形成一个可复用的系列**

建议先定“温暖的玩具绘本风”母版：固定三分之四视角、车辆默认车头向右、共同的地面基线、圆润清楚的轮廓、暖色底和明确功能色、少量纹理、统一阴影方向。卡片中的车与场景中的车属于同一个模型家族；地图真有需要时，再为一小部分车辆补俯视图。

先制作一张样板场景及 6 辆代表车，验证它们在 iPad 卡片尺寸下是否容易区分，再批量扩大。数量可以从 12 种起步，逐步到 24 种真实车型：救援、工程、运输和生活服务各一组。换色和导出角度属于变体，不算作新的车型。

| 素材层 | 建议的阶段目标 | 用法 |
| --- | --- | --- |
| 基础车辆 | 12 种起步，成熟版本约 24 种 | 分类、配对、记忆、数独与城市场景共用 |
| 车辆状态 | 待命、行驶、执行一种本职动作 | 车轮、车身、灯、车臂等分层，避免每一帧都重画整辆车 |
| 场景 | 车库/仓库、街区、工地、消防站 4 套模块 | 用道路块、地面、建筑和前景组合关卡 |
| 道具 | 约 30–40 件可辨识物品 | 轮胎、路锥、桥板、箱子、油桶等；建立明确语义与碰撞/摆放区域 |
| 引导角色 | 1 个小车站角色及少量表情 | 负责欢迎、疑惑、帮助和结束；不需要每次操作都评价孩子 |
| UI 图标 | 约 20 个同一风格的功能图标 | 替换菜单和游戏中的系统 emoji |
| 声音 | 约 15–25 个短音效，精选提示语音 | 装配、轮子轻响、落板、到站、提示等都与具体动作对应 |

可以采用统一素材包或定制母版后批量生产。若使用 AI 辅助，先建立角色和车辆参考表，逐批审核视角、车轮、颜色和比例，必要时重新分层绘制。两幅找不同画面应由同一场景数据生成，再显式修改几个部件；分别生成两张图会产生不可控差异。

素材清单至少记录 assetId、车辆/部件语义、视角、可用状态、来源、许可、版本、锚点和缩略图。原始编辑文件与运行时导出文件分开保存。

可作为候选的统一资源：Kenney 的 [Toy Car Kit](https://kenney.nl/assets/toy-car-kit) 标注 100 个文件、CC0，属于 3D 套装；[Car Kit](https://kenney.nl/assets/car-kit) 标注 45 个文件、CC0。文件数不代表车型数。这类套装可以统一灯光和镜头后预渲染为 2D 素材；是否符合本项目风格要先做样板，不能把多套不同风格直接混用。

**声音需要成为统一的产品能力**

现有音频已经预生成，运行游戏时不用连接 TTS 服务，这是可以保留的方式。先把声音接入做稳定，再决定是否升级部分旁白的制作质量。

推荐分为语音、操作音效、环境/音乐三个通道。语音优先，环境音自动降低；记忆和听觉指令阶段可以关闭无关背景音。背景音乐默认关闭或很轻，由家长控制。反馈音短、柔和且一致；不使用刺耳失败音和持续警报。现场录制或合成的声音都应经过逐条听审和统一音量处理。

把 `speakGently('一整句中文')` 逐步改成按 ID 请求，例如 `voice.play('traffic.green')`。文案和音频版本共同受清单管理；构建前确认每个引用存在，排查遗留文件。通用安慰语可以作为被明确请求的内容，不应悄悄替代缺失的任务说明。

开始按钮同时承担声音初始化：在用户点击时创建/恢复 AudioContext，随后显示可见的声音状态。页面挂载或切换到子组件时自动播放，不能被视为可靠的声音解锁动作。Safari 和主屏幕网页 App 都要验证开始、重播、静音、后台恢复、网络失败和设备旋转。相关依据见 [Web Audio 最佳实践](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices) 和 [WebKit 的媒体用户手势说明](https://webkit.org/blog/6784/new-video-policies-for-ios/)。

声音调度还要处理优先级：任务说明可以打断短表扬，表扬不要打断下一段指令；进入游戏时的介绍不要被挂载后的另一段声音立刻截断；暂停立即停止所有通道。快速连续触碰需要节流音效，但不应为了听完整段旁白强迫孩子等待。

  rescue/                    救援队：规则、关卡生成、场景、配置
  garage-memory/             车库记忆小游戏

  game-session/              开始、演示、操作、反馈、暂停、结束

每个游戏至少有：元数据、规则与状态、关卡/随机题生成器、难度参数、素材依赖、交互界面和规则测试。用统一 registry 派生大厅、家长列表和记录 API 的允许列表，减少添加一款游戏时到处修改字符串。

共同生命周期建议明确为：加载资源 → 看一遍教学 → 孩子操作 → 动作反馈 → 下一小步 → 本局结束。暂停是可恢复的状态，不能顺便重置题目或改变规则。卡片和排排看可以继续用 React + SVG；需要大量精灵移动和场景交互的游戏，再评估单独接入 Phaser。Phaser 官方支持 WebGL/Canvas 与 React 等前端框架的协作，但换引擎本身不会补足玩法和美术设计：[Phaser 官方文档](https://docs.phaser.io/)。

当前有较多 Sites 运行脚本、连接器示例和通用 UI 模板。清理前检查真实导入关系；保留站点构建和登录依赖。依赖包出现在 package.json 不代表全部会进入游戏首屏，应以实际产物与加载情况决定优化。`README.md` 和 `QA.md` 中仍有旧设备语音、旧登录及历史验证表述，应补一个明确的“当前状态”，避免把旧验证当成当前版本的实机证明。

**工作记忆、视觉记忆与亲子价值的边界**

认知目标可用于决定“这一关需要孩子做什么”。视觉观察是信息一直在眼前时比较和寻找；视觉短时记忆是信息收起后保持并辨认；视觉空间记忆涉及位置或路线；工作记忆进一步涉及保持信息、按规则使用它并更新。不同任务会同时动用多个过程，不需要把每款游戏包装成单一能力测量工具。

执行功能研究中，练习任务或相近任务上的进步不等同于广泛的现实迁移。不同综述结论有差异，较新的学龄前干预综述也报告了较小、因领域而异的效果。因此，游戏应描述为提供练习机会，避免把通关数换算成“注意力提高多少”或情绪能力分数。[执行功能综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC4084861/)；[儿童执行功能近迁移/远迁移元分析](https://pubmed.ncbi.nlm.nih.gov/30652908/)；[3–6 岁干预系统综述与元分析](https://pubmed.ncbi.nlm.nih.gov/41491942/)。

亲子设计需要让成人真正参与：共同讨论路线、互相出题、轮流扮演司机和调度员、用真实玩具车继续同一个规则。屏幕能记录按钮操作，不能确认是谁完成的、是否独立理解、真实情绪是否改善。[Harvard 分龄游戏活动指南](https://developingchild.harvard.edu/resources/handouts-tools/activities-guide-enhancing-and-practicing-executive-function-skills/)；[AAP 关于共同观看和游玩](https://www.healthychildren.org/English/family-life/Media/Pages/watch-together.aspx)。

**实施顺序与完成标准**

| 阶段 | 做什么 | 可以交付和判断的结果 |
| --- | --- | --- |
| P0：统一基础体验 | 统一声音状态、暂停、输入过渡、提示 ID、教学阶段；确定一套美术母版；整理游戏 registry | 不再出现有按钮却无法知道声音状态、不同页面静音不一致、连点跨步骤的问题；一款样板关完整走通 |
| P1：快递站精品 | 先用 6–12 辆代表车，完成装货/出发/到站/卸货；做教学与 6–8 个基础关卡 | 孩子看过演示能开始；记忆版本确实在回忆阶段隐藏信息；提示后仍能完成一轮并自然结束 |
| P2：统一素材与记忆小游戏 | 扩展到约 24 种车和 4 组场景；制作少了谁、停在哪里、翻翻配对 | 同一车辆在各游戏有一致身份与风格；题目变化受控，没有视觉答案歧义和不可解题 |
| P3：救援队精品 | 把红绿灯、轮流桥、改道组合为有明确单关目标的场景 | 车辆动作与规则一致，家长有实际角色，遇到变化可以重试和求助 |
| P4：持续发布能力 | CI 中运行规则/资源校验与构建；记录 gameVersion 和配置；版本说明；按需完善账户隔离 | 新增一款游戏不复制整套大厅/声音/记录代码，发布有可回查版本；扩大受众时记录隔离可验证 |

每个可上架游戏都应通过同一套体验验收：无需识字即可理解主要操作；输入目标清楚且适合手指；正确操作产生看得懂的场景结果；错误反馈具体且温和；求助、暂停、退出随时可用；不会自动开启下一局；横竖屏、Safari 与主屏幕入口、声音和后台恢复都有实机记录。

规则测试继续验证随机题的可解性、唯一性或合法性、故意设置的差异数、出题分布和重复操作。新增浏览器验证重点覆盖开始/教学/暂停/退出/声音/连续重玩等整条路径；长期也需要真实亲子陪玩反馈，例如哪段需要家长反复解释、哪种规则变化带来挫败、结束后是否愿意在线下继续同一游戏。这些观察用于产品改进，不自动生成儿童能力评价。

优先投资顺序建议为：一款完整好玩的体验 → 一套可复用的素材 → 稳定声音与游戏生命周期 → 有控制的关卡变化 → 更多游戏。首个迭代完成后再用亲子试玩结果调整第二款，避免一次铺开过多尚未打磨的玩法。
