**儿童和家长的使用流程**

保留 `/game` 为主屏幕入口。大厅突出一张有完整插画的“去快递站”卡片，并保留现有小游戏入口；儿童看到具体地点和行为，认知目标和难度说明放在家长入口。快递站采用可直接进入的 `/game/delivery` 路由，沿用当前 Sites/OpenAI 访问控制。

第一次进入先看一个短演示：货物从货架进入车厢，车开到站点，货物卸到地面。演示可以重看，也可以由家长跳过。之后只要求孩子做一个已经演示过的动作。首次进入时，开始按钮同时承担声音初始化，不依赖页面挂载后自动播放。

每关包括 3 次短配送任务。每个任务完成后由孩子或家长主动继续；三次结束后车辆回库，家长决定重玩、换关或结束。始终提供暂停、求助和结束。游戏不设置倒计时、扣分、排行榜、连续签到或自动开下一局。

亲子角色可以交换：一人记订单/装货，另一人确认车辆准备好或协商下一站。页面说明谁该操作，但系统只记录发生的操作，不声称能识别是谁点击，也不推断孩子是否独立理解。

**快递站的交互与记忆机制**

基本过程为：查看订单 → 确认看好了 → 选择货物 → 装车 → 车辆出发 → 到站 → 卸货 → 下一次任务/本关结束。点击是首要操作；车辆与货物以动画响应。拖拽如加入，必须保留点击完成同一任务的方式。

熟悉模式保留订单，主要学习操作和物品匹配。视觉记忆模式在孩子点“记好了”后收起订单，再让孩子选货。顺序记忆模式保留目的地图示教学，熟悉后收起，按听到或看到的顺序到站。更新任务先记住两件货物，交付一件后再想起剩余目标。

记忆模式的回忆阶段，订单不能继续展示答案；若车厢里的物品会暴露答案，则以统一封闭箱体表现。语音重播、辅助图标和当前步骤高亮也不能无意给出答案。孩子主动重看/重听时恢复必要支持，记录为支持使用，不扣分、不评价记忆好坏。

更新任务的早期版本不同时要求记路线和复杂装货：第一站由清楚的场景引导，交出指定物品后，剩余车厢内容仍收起，再选择要送到下一站的物品。这样每次任务的主要挑战清楚可控。

错误反馈采用三层：第一层指出当前可观察的规则；第二层缩小寻找范围；第三层完整演示一次动作。示范后保留机会让孩子自己再做。场景保持，车辆不爆炸、不倒退惩罚，也不以声光效果夸大错误。

**八个关卡模板**

每个模板生成 3 次小任务，题目来自经过筛选的车辆、物品和目的地集合。模板决定规则，随机种子仅提供规则内的变化。以下数量为产品起始参数，不是儿童年龄常模。

| 模板 | 核心内容 | 起始设置 | 支持与进阶 |
| --- | --- | --- | --- |
| 1. 小车第一次送货 | 熟悉看订单、装一件、送达 | 1 件物品、2 个清楚的选项，订单常驻 | 手把手演示后再操作 |
| 2. 两件装备一起送 | 熟悉两件物品的装卸 | 2 件不同物品、3 个选项，订单常驻 | 不增加记忆要求，先理解装两件 |
| 3. 看好了再装车 | 视觉记忆保持 | 2 件物品，孩子主动收起订单 | 可以重看；先用差异明显的物品 |
| 4. 货架多了一点 | 保持熟悉记忆长度，增加干扰 | 仍为 2 件物品，选项由 3 增至 4 | 不同时增加记忆物品数量 |
| 5. 认识两个站点 | 学习顺序规则 | 两站，路线卡常驻，逐站演示 | 这是新规则教学，不强行隐藏提示 |
| 6. 听完按顺序送 | 听觉顺序记忆 | 熟悉的两站，开始执行后收起路线卡 | 可以重听和请求家长讲解 |
| 7. 送走一件还剩谁 | 保持并更新剩余目标 | 两件物品交付一件后，选择剩余目标 | 车厢答案收起；路线保持简单 |
| 8. 换辆车再试试 | 在相同规则下巩固 | 家长选择熟悉的保持或更新模式，换车/站点装饰 | 不叠加多项难度，不自动变成综合测试 |

不以年龄锁定或星星解锁这些模板。家长可以固定在熟悉关反复玩。新游戏在本关内保持参数稳定；升级建议只在结束时出现，孩子/家长主动选择。连续两局顺利且没有使用提示等支持时，可以建议尝试下一档，界面不把它写成能力已掌握。

保存模板 ID、随机种子、实际参数和素材版本以便复现。通过题目签名避免近期完全重复；不能因去重而生成超出模板或无解的题。生成器要使用分散的种子验证题目分布。

**美术与素材交付**

确定一套温暖的玩具绘本风母版：统一三分之四视角、车辆默认车头向右、固定地面基线、清楚的大轮廓、共同阴影方向、少量纹理。功能色要可辨认，规则也用形状/图标表达，避免只靠颜色。

先做消防车、快递车、挖掘机三种代表车和一个仓库小场景，检查小尺寸辨识、车辆比例和动作，再扩到 12 种：消防车、救护车、警车、公交车、厢式货车、快递车、挖掘机、吊车、搅拌车、压路机、拖车和垃圾车。

12 种车辆均提供待命与行驶表现。行驶优先复用车身、车轮/履带分层和少量运动，不为每个状态重复导出整张大图。快递站实际用到的车辆另外制作装货/卸货状态；车臂、搅拌筒等专属功能动作按本轮真实使用需求制作。

首批道具为轮胎、工具箱、软管、水桶、头盔、路锥、路障牌、桥板、木箱、包裹、油桶和梯子。场景分为仓库、消防站与工地；共享道路、地面和摆放位置。道具语义要明确，记忆题初期不采用形状近似又难区分的多个箱子。

共同控件采用同一图标家族：开始、返回、暂停、重播、求助、提示、继续、结束、语音、音效等。新大厅、新游戏和车辆卡片中的系统 emoji 逐步替换。旧版六种车辆通过适配器映射到新素材 ID，原有分类与数独的合法车型集合保持明确。

资产登记内容包括：assetId、语义/车型、视角、状态、部件、尺寸、锚点、来源与许可、版本、所属资源组。原始编辑文件和运行时导出文件分别保存。先确定同一个母版系列，再进行批量生成或绘制；每批素材人工检查，不以换色数量充当车型数量。

**语音、音效与合包方案**

继续使用预生成的完整句子录音。现有 edge-tts 生成流程作为素材制作工具，游戏运行时读取发布后的音频文件。新增文本先组合成整句再生成，不在播放时把“先去”“加油站”等词语机械拼接。温柔女声的音色、语速和响度保持统一；任务指令简短明确，避免每次操作都长篇表扬。

快递站首先制作约 24–36 条核心完整语句，实际数量以锁定的关卡文案和提示清单为准：入场和教学、看订单、确认记好了、装货/送达、顺序指令、帮助、暂停恢复及回库。动态组合用受控物品和地点集合生成完整录音，并检查所有可达组合有资源。

首批 12 个短音效：按钮轻点、选择、轻拾起、装货入槽、车门关闭、轻启动、低声行驶循环、温和停车、卸货落位、到站、求助回应、本关结束。音效与画面动作绑定；没有点击失败蜂鸣或持续警笛。

声音服务提供语音、音效、环境/音乐三个通道。背景音乐默认关闭，本轮如需要仅准备一段轻环境音。语音播放时降低背景通道；听指令和回忆阶段抑制无关声音。全站共享静音与分通道设置，暂停/后台立即停止或暂停相应通道，恢复不重叠播放旧提示。

资源合包遵循：

- 短音效构建为一个小音频精灵包及起止索引，运行时按稳定 ID 播放。
- 语音以完整语句保留，按通用/游戏/关卡组缓存与预取；先不把全站语音合成长文件。
- 可分层、换件、变色的车辆或控件保留 SVG 能力；采用栅格素材的道具/动画帧按实际使用组生成图集和索引。是否启用某组图集由真实体积与加载测量决定。
- 场景背景单独压缩，避免被少量控件拖进一个必须整体下载的大图。
- 原始文件保持独立，构建脚本自动生成导出包、索引和内容版本；不手工维护时间偏移或图集坐标。

音效合包前统一采样、响度和头尾静音，保留必要间隔，实测切片边界与循环，避免串入相邻声音。界面调用 `voice.play('delivery.order...')` 或 `sfx.play('cargo.load')` 这样的稳定 ID；发布前校验缺失、未引用、重复和损坏资源。

当前全站已有 96 个 MP3、92 条清单记录。迁移先建立明确旧提示兼容表，补齐缺失句子，再删除确认未被引用的遗留文件。匹配不到任务说明时提供准确图文、声音状态和重试，不悄悄换成无关通用录音。

**加载与性能预算**

大厅仅加载大厅控件和入口缩略图。点击进入快递站后优先准备当前场景、当前车辆、首个任务和通用音效；游玩期间低优先级准备下一任务。所有资源组提供加载中、失败重试和可继续图文游玩的处理。加载状态不伪装为卡住的游戏。

首轮以“大厅至快递站第一任务的核心资源累计压缩体积约 3 MiB 以内”作为设计预算；首次登录页面和浏览器自身资源不计入该数字。已缓存短音效的点击到发声以不超过约 150 ms 为目标；动画尽量保持流畅，在目标 iPad 上记录实际表现。这些是待实测的工程目标，不是当前已达到的结果。

测量冷缓存首次进入、暖缓存重进、语音首次播放、下一任务切换、解码后音频内存和纹理尺寸。包越少不必然越快，资源分组、实际传输体积、解码时间与播放延迟共同决定是否值得合包。

资源文件采用版本化名称或内容哈希，发布后可缓存；页面、身份与家长记录继续使用适合其用途的缓存策略。声音和素材缓存不等于完整离线游戏，本轮仍按联网使用验收。

**工程拆分与兼容策略**

采用现有 React/Vinext/Worker/D1 技术基础。快递站先用 React、SVG 与 CSS 表达可控的点选和场景动作。后续复杂地图游戏需要更密集的精灵运动时，再评估单个游戏的渲染引擎。

建议增加以下职责目录，按功能逐步迁移，不一次移动全部模板文件：

```text
games/registry.ts                 游戏元数据与资源组入口
games/delivery/model.ts           规则、阶段与动作
games/delivery/generator.ts       关卡模板和随机题
games/delivery/levels.ts          8 个关卡参数
games/delivery/scene.tsx          新游戏场景与输入
shared/game-session/              局次、暂停、进度和过渡
shared/audio/                     解锁、通道、优先级、播放状态
shared/assets/                    车辆/道具目录与加载器
shared/ui/                        共用游戏控件
content/                          文案、素材清单、资源分组
assets/source/                    原始创作素材及来源记录
public/assets/                    构建后的运行素材
scripts/assets/                   导出、音频合包、校验与资源报告
app/game/delivery/page.tsx        新游戏入口与访问控制
```

生命周期明确区分加载、教学、查看信息、回忆/操作、动作反馈、下一任务和结束；暂停保存其原阶段。动画过渡时重复触碰不跨越多个步骤，也不增加错误次数。旋转屏幕与尺寸变化仅调整布局，不生成新题。

注册表作为游戏入口、家长名称、记录允许列表和资源组的共同来源。旧游戏经适配器接入声音和共用控制；原有规则 reducer 和测试保留。新 ID 不能让旧分类/数独生成器突然使用未配置用途或颜色的车辆。

优先修复已发现的跨游戏问题：大厅与 LegacyGame 静音状态不一致、RoadGame 部分暂停未停止声音、缺失提示的无关录音兜底、连续同色红绿灯连点跨步。统一锁定输入的依据是当前阶段和过渡动作，不增加随意的长时间等待。

**家长设置、进度和记录**

本轮支持固定熟悉模式、视觉记忆模式、顺序记忆模式和更新模式；关卡参数与支持程度分别管理。进度保存当前模板、教学是否看过、家长固定的支持方式和声音偏好。优先保证本机恢复稳定，既有局次记录继续服务端同步。

记录扩展包含 gameVersion、levelId、seed、实际参数和使用的支持方式，并继续保存完成/主动结束、错误、提示、重试、暂停等可确认汇总。扩展字段通过向后兼容的数据库迁移加入，旧记录仍能显示。避免逐次点击轨迹、儿童姓名、照片或录音。

日期/游戏筛选移至服务端，以覆盖全部记录，而非只过滤当前已加载的 50 条。写入去重、同源校验、离线待同步提示和手动清空继续验证。数据用于回查题目和改进产品，不换算成注意力、记忆或情绪能力评分。

本轮继续当前家庭私密访问设置。以后扩大到其他家庭前，先做账户/家庭维度的数据隔离；当前全站记录查询与清空不能直接作为多家庭共享实现。

| B：共用声音与资源 | 稳定 ID、声音解锁与状态、短音效合包、资源清单/校验、按需预取 | iPad 声音开启入口清楚；加载失败可恢复；声音与素材有可回查版本 |
| C：完整单关 | 查看/收起订单、点选装货、行驶、卸货、暂停与三次任务后回库 | 一关从进入到结束完整可玩；记忆阶段不泄露答案；连点和暂停不改变题目 |
| D：关卡与素材扩展 | 8 个模板、12 种车型、12 件道具、3 个场景、完整提示与动作 | 变化受控、初级题容易辨认、帮助和演示能完成任务，没有占位素材 |
| E：接入与回归 | 大厅入口、旧游戏声音兼容、记录/进度、筛选与迁移、自动检查 | 新旧入口都能使用；旧记录可读；关键路径与规则检查通过 |
| F：发布与陪玩验证 | GitHub 提交、Sites 构建发布、路由/权限核对、目标 iPad 陪玩 | 给出线上链接、提交、发布版本及验证清单，记录实际需要解释/调整的地方 |

阶段之间按依赖推进。素材扩展在样板建立后进行；共同声音先满足一关，再覆盖全部模板。每个阶段结束都留下一个可检查的结果，减少末尾同时发现玩法、美术和声音不匹配的风险。

**验收清单**

- 初次进入有可重看的动作示范；孩子无需识字就能辨认主要操作。关键控件以适合手指点击的约 64–80 CSS px 目标设计，并在实际 iPad 上检查间距和可达性。
- 每次正确操作产生语义一致的场景变化，例如物品进车厢、车辆到站和物品落位；反馈不能只有答对文字。
- 记忆任务在回忆阶段收起必要信息，教学模式保留支架；主动重听/重看不触发惩罚。
- 8 个模板均可以完成和重复游玩，题目参数和随机种子可回放；同一任务不会生成无解、目标缺失、答案歧义或明显偏斜的选项。
- 连续触碰不会跨越动作阶段、重复装货、重复结算或重复写记录；被忽略的过渡期输入不计错。
- 暂停、后台切换、返回、重进和旋转后状态一致；继续不会同时重播多段声音或自动生成新题。
- 语音、音效和环境音设置全站一致；开启、静音、重播、加载失败和恢复都有明确状态。第三层提示真正示范操作。
- 每关三次任务后主动结束，家长决定是否继续；任何阶段可以求助或结束。
- 家长记录按日期和游戏查询准确；重复请求去重、同步失败提示和清空范围正确；迁移后旧数据可读。
- `/`、`/login`、`/game` 和新游戏路由符合当前登录与访问控制；静态素材缓存不改变页面和记录访问保护。
- 横屏/竖屏布局、Safari 与主屏幕网页 App 的声音、登录和后台恢复分别有验证记录。

**验证与发布安排**

自动验证沿用现有三组规则测试，补充新游戏中确实重要的规则和生成器性质，例如答案隐藏阶段、物品更新、过渡输入、题目可解性和可复现性；避免为简单组件编写只复述实现的测试。资源检查确认引用存在、包索引合法、音频/图集边界正确、来源信息完整。

浏览器验证走完整流程：首次打开 → 开启声音 → 看教学 → 完成三次配送 → 主动重玩 → 中途求助/暂停 → 返回大厅 → 查看记录，并覆盖资源加载失败和重试。生产构建、类型检查和这些关键检查接入 GitHub CI；需要的构建资源预先生成并随可发布代码版本保存，CI 不依赖临时在线 TTS 生成。

发布顺序为：完成代码与资源 → 本地检查 → 提交并推送 GitHub 功能变更 → 通过检查后合入 main → 将同一提交推至当前 Sites 源仓库 → 构建对应归档 → 保存并发布该版本。保持既有站点访问范围，最终提供 `/game` 与 `/game/delivery`。若 CI 或其他机制导致需要重新提交，Sites 归档也必须从最终推送状态构建。

发布记录写清 Git commit、产品版本、Sites 实际版本及部署结果。数据库迁移采用兼容增加字段的方式，确保需要回退应用版本时仍可读取已有数据；保留上一个可部署版本。登录、资源和服务端记录的验证按平台边界分别记录。

桌面浏览器尺寸模拟与真实 iPad 检查分别列出。家长在真实设备上完成首次声音、主屏幕登录、旋转、后台恢复和一次完整亲子陪玩的核对；若无法取得实机反馈，明确标记该项待确认，不把模拟测试写成实机通过。

最终交付包含：完整源码、素材原稿与来源清单、运行时资源和合包索引、音频生成/资源构建脚本、数据库迁移、8 个关卡配置、规则与资源检查、更新后的 README/QA/发布说明、GitHub 提交链接及 Sites 游戏链接。
